# EFBCrewIdentity

驾驶舱共享平板上的**机组身份核验、会话交接、双人放行签字**库（Swift 6，无第三方依赖）。

面向的场景：一台 iPad 电子飞行包（航图 + 性能计算 + 放行签字），会在不同机组之间交接。
需要防住两件事：

1. **有人借用别人的账号完成签字**；
2. **交接时上一位机长的登录状态没清掉**，下一段航班的签字被记到上一人名下。

同时必须满足驾驶舱的真实约束：

| 约束 | 本库的应对 |
|---|---|
| 经常没有网络 | 全部核验离线完成；联网只用于本场预置（时间锚 / 撤销名单 / 令牌） |
| 飞行员戴手套 | Face ID 不需摘手套，作为"人在场"因素；PIN 只在开始值班时输一次 |
| 起飞前时间紧 | 每次签字 ≈ 一次 Face ID + 一次点击；令牌与证书均已预置 |
| 正副驾驶同一设备分别签字 | 左/右座各签发一次，第二签内嵌第一签摘要形成互锁 |
| 离线签字落地后要被公司核实为本人所为 | 硬件密钥签名 + 公司根签发证书 + 一次性令牌 + 时间锚，公司只凭公开材料离线复核 |

---

## 安全模型：三个因素，离线可全部完成

签字当时必须具备：

1. **知道** —— 每位机组各自的 PIN（存在本机，用 PBKDF2 派生校验）；
2. **持有** —— 该机组在 Secure Enclave 内、**不可导出**的 P-256 私钥（证书绑定这颗公钥）；
3. **在场** —— 签字瞬间的 Face ID（手套可识别），每次签字都做。

三者叠加才签发一次性 `SignatureGrant`；grant 只允许一次签字使用。

> 关键取舍：PIN 门禁的作用域是**一次值班会话**（开始值班输一次），
> 而"人在场"门禁是**每次签字**。这是为戴手套与时间紧的场景所做的刻意设计，
> 并由策略（`CrewPolicy`）可调。

---

## 一次性令牌：离线时的"公司授权"

离线无法实时查询"这班是否被公司放行"。于是公司在本场为每个航班**预发一次性令牌**：

- 每枚令牌绑定 `航班 + 座位 + 机组 + 设备 + 用途 + 时间窗`，由公司签发；
- 签字时消耗对应令牌，序列号写进签字记录；
- 落地后公司凭自己的签发清单确认：这枚令牌确实发给了这位机组、这一航班，且只用过一次。

这让"借用他人账号"即便拿到 PIN 也无效 —— 令牌是按人发货的，借用者名下没有这枚令牌。

---

## 时间：改设备挂钟也没用

签字时间必须能被公司核实。做法：

- 联网时公司签发**时间锚**（`TimeAnchor`：权威 UTC + 设备单调时钟读数 + 有效期）；
- 离线期间以单调时钟（`mach_continuous_time`）推算，用户无法调整；
- 设备重启会让单调锚失效，必须重新联网同步；
- 签字同时封存 `TimeAttestation`，公司结合自己签发的锚回执即可精确重算。

---

## 会话交接：状态必须在交接那一刻消失

`SessionManager` 强制：

- 每个座位同一时刻最多一个活跃会话；
- 座位被占用时，新机组**不能**直接顶替：要么旧会话已结束，要么持有主管签发的一次性**接管授权**；
- 交接提交的同一刻，旧会话 `dispose()`，其 SE 密钥门禁立即 `lock()`，所有 grant 作废；
- 同一机组不能同时占两个座位；
- 每段无人值守空窗（`custody gap`）都被记录；超过策略阈值须显式确认。

---

## 落地后的公司侧核验

`ReleaseAuditor` 只凭公开材料（公司根公钥、签发清单、令牌清单、锚回执）离线复核，
逐条给出结论（30+ 项），覆盖：

- **A 证据完整性**：逐字节重建被签载荷、内容摘要、ECDSA 验签、记录摘要；
- **B 身份与授权**：证书链到根、证书绑定的机组/设备/公钥、令牌归属与唯一性、吊销状态；
- **C 双人与互锁**：两名不同机组、左右座、第二签包含第一签摘要、双签间隔、审计链完整；
- **D 时间**：时间证明与锚回执自洽。

任何一项被篡改都会落到具体失败项，便于复核人员看到"为什么可信 / 哪里存疑"。

## 模块划分

```
EFBCore          规范化 JSON、标识符、时间锚、审计散列链、策略
EFBCryptography  Secure Enclave 签名密钥、PIN 派生与包裹、Face ID、Keychain、密封
EFBIdentity      机组证书、凭据存储、解锁、按次签字授权、PIN 管理、预置流程
EFBRelease       一次性令牌、双人签字、公司侧核验、本地归档与上传队列
EFBSession       座位会话、交接、接管授权、空闲锁屏
EFBProvisioning  本场预置包与校验、CockpitApp 装配层（唯一需要网络的步骤）
EFBCompany       公司侧签发工具 —— 不应编译进平板应用
efbdemo          可读的端到端演示
efbverify        150 项断言的校验器（CI 入口，含对抗性攻击场景）
```

依赖方向严格单向：`EFBIdentity` 与 `EFBRelease` 互不依赖；共享的预置类型与同时用到它们的装配层 `CockpitApp` 放在 `EFBProvisioning`，避免循环依赖。平台无关，可在 macOS 上测试。

## 运行

```bash
swift build
swift run efbverify     # 逐条断言；有失败则退出码非零
swift run efbdemo       # 阅读式演示：预置 → 双签 → 公司核验 → 交接
```

### 平台说明

- 核心库与校验器在 macOS 上完整编译并运行；
- iPad 专属适配层（真实 `SecureEnclave` + `LAContext` + `Keychain`）在 `EFBIdentity/IOSPlatform.swift`，
  由 `#if os(iOS)` 隔离，需要 Xcode + iOS SDK 才能编译；
- 本机只有 Command Line Tools（无 XCTest / swift-testing），因此测试是一个可执行的断言校验器。

### 测试里为什么用软件密钥？

带 `.applicationPassword` ACL 的 Secure Enclave 密钥在 headless 环境会拉起系统 UI
（本机实测会挂起），因此协议测试使用 `SoftwareKeyVault`（同样不可导出、同样的 PIN 门禁与
`lock()` 语义）；而 **真实的 Secure Enclave 生成 / 签名 / 验签 / 密封** 由独立套件在硬件上验证。

## 经过了什么验证

- 150 项断言的自动化校验器（`swift run efbverify`），覆盖：规范化编码、时间锚（含重启冻结时间攻击）、
  Secure Enclave 真实密钥、PIN 锁定与改 PIN、双人签字与互锁、公司离线核验的 30+ 项检查、
  篡改检测（内容/时间/身份/审计链/令牌/航班）、交接与接管、竞态（核验期间被交接）、座位占用、
  归档上传、预置包校验。
- 两轮**独立对抗性审计**：第一轮由实现过程自查，第二轮由独立代理专门尝试击穿 6 条安全性质。
  发现的缺陷（PIN 锁定失效、预置根可被替换、重启冻结时间、审计链尾未锚定、时间自证、硬件声明自报、
  接管授权可重放、撤销名单不生效、令牌重启复活、委托字段不校验）**均已修复并有断言锁定**。
  详见 `DESIGN.md` 第 6、8 节。
